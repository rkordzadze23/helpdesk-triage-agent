# Helpdesk Triage Agent (ეტაპი 1)

**ავტორი:** რატი კორძაძე (ინდივიდუალური პროექტი)
**კურსი:** LLM-ზე დაფუძნებული აგენტი - ეტაპი 1 (კონცეფცია და მუშა ჩონჩხი)
**გამოყენებული მოდელი:** `qwen2.5:7b` (ლოკალურად, Ollama-ით; cloud API არ გამოიყენება)

ეს არის ლოკალური AI აგენტი, რომელიც მომხმარებელს ეხმარება Windows-ისა და IT-ის გავრცელებული პრობლემების გადაჭრაში. ენობრივი მოდელი კითხულობს მომხმარებლის პრობლემას, **თვითონ წყვეტს**, სჭირდება თუ არა ლოკალურ ცოდნის ბაზაში ძიება, და ძიების შედეგზე დაყრდნობით წერს პასუხს.

> ეს მხოლოდ **პირველი ეტაპია** (აგენტი + ლოკალური LLM + ერთი მუშა ინსტრუმენტი). სისტემური ლოგების ან დიაგნოსტიკური მონაცემების ანალიზი ჯერ არ არის დამატებული.

## A. პროექტის მიმოხილვა

**პრობლემა.** ბევრ ყოველდღიურ კომპიუტერულ პრობლემას (ნელი კომპიუტერი, Wi-Fi-ს არქონა, პრინტერი "offline"-ია, დისკი გაივსო) კარგად ცნობილი გადაწყვეტა აქვს. მიუხედავად ამისა, მომხმარებელმა ხშირად არ იცის, საიდან დაიწყოს, ან ინტერნეტში შემთხვევით ნაპოვნ სახიფათო რჩევებს მიჰყვება (registry cleaner-ები, სისტემური ფაილების წაშლა). IT მხარდაჭერის გუნდებიც ბევრ დროს ხარჯავს ამ განმეორებად პირველი დონის შეკითხვებზე.

**გადაწყვეტა.** მომხმარებელი პრობლემას ჩვეულებრივი ტექსტით აღწერს. აგენტი ეძებს წინასწარ მომზადებულ ლოკალურ ცოდნის ბაზაში და შემდეგ განმარტავს შესაძლო მიზეზებს, რა უნდა შემოწმდეს პირველ რიგში, რომელია უსაფრთხო ნაბიჯები და როდის უნდა მიმართოს მომხმარებელმა IT მხარდაჭერას. პროგრამა მთლიანად ოფლაინ მუშაობს: არ იყენებს ფასიან API-ს და არც ღრუბლოვან (cloud) LLM-ს.

**სამიზნე აუდიტორია.**
- უნივერსიტეტის ან მცირე ორგანიზაციის სტუდენტები და არატექნიკური თანამშრომლები.
- პირველი დონის IT მხარდაჭერის თანამშრომლები, რომლებსაც სწრაფი და ერთგვაროვანი საწყისი წერტილი სჭირდებათ.

## C. გარემოს თვისებები

1. **ნაწილობრივ დაკვირვებადი** - აგენტი მხოლოდ იმას ხედავს, რასაც მომხმარებელი წერს, და კომპიუტერის რეალურ მდგომარეობას ვერ ამოწმებს, ამიტომ პრობლემის ნამდვილი მიზეზი მისთვის დაფარული რჩება.
2. **სტოქასტური** - ერთი და იგივე რჩევა სხვადასხვა კომპიუტერზე სხვადასხვა შედეგს იძლევა, რადგან შედეგი დაფარულ ფაქტორებზეა დამოკიდებული (გარდა ამისა, LLM-ის ფორმულირებაც იცვლება გაშვებიდან გაშვებამდე).
3. **თანმიმდევრული** - ერთი ბიჯის პასუხი წინა ბიჯებზეა დამოკიდებული (საუბრის ისტორია), ხოლო აგენტის ადრინდელი რჩევები განსაზღვრავს, რას სცდის მომხმარებელი შემდეგ.
4. **დინამიკური** - კომპიუტერის მდგომარეობა შეიძლება შეიცვალოს მაშინაც, როცა აგენტი "ფიქრობს", და ბიჯებს შორისაც (ინსტალირდება განახლება, პროგრამა ითიშება, მომხმარებელი რაღაცას სცდის).
5. **დისკრეტული** - პერცეპტები და მოქმედებები სასრული სიმრავლეა: ტექსტური შეტყობინებები, დისკრეტული ბიჯები, ინსტრუმენტის ფიქსირებული გამოძახებები და ცოდნის ბაზის ჩანაწერები.
6. **ერთაგენტიანი** - მიზნის მისაღწევად მოქმედებს მხოლოდ ერთი აგენტი, ხოლო მომხმარებელი მოთხოვნის წყაროა და არა კონკურენტი ან პარტნიორი აგენტი.
7. **ცნობილი** - აგენტის სამყაროს წესები სრულად განსაზღვრულია, რადგან ინსტრუმენტის ქცევას, მის შემავალ/გამომავალ მონაცემებს და ცოდნის ბაზის შიგთავსს დეველოპერი აზუსტებს (კომპიუტერის დაფარული მდგომარეობა აქ არ შედის, ის *ნაწილობრივ დაკვირვებადობაშია* ასახული).

## D. აგენტის ტიპი

**მიზანზე ორიენტირებული აგენტი (goal-based agent)** მარტივი შიდა მდგომარეობით (საუბრის ისტორია).

**რატომ სწორედ ეს ტიპი (გარემოს თვისებებზე დაყრდნობით):**

- **არა simple reflex.** გარემო *ნაწილობრივ დაკვირვებადია* და *სტოქასტური*, ამიტომ ერთი მიმდინარე შეტყობინება ხშირად საკმარისი არ არის სწორი რეაქციისთვის. აგენტმა უნდა გადაწყვიტოს, სჭირდება თუ არა ძიება და რა ფრაზით, და ეს წინასწარ დაწერილი "თუ X, მაშინ Y" წესებით არ გადაიჭრება.
- **მიზანზე ორიენტირებული.** აგენტს ცხადი მიზანი აქვს: მომხმარებელს მისცეს უსაფრთხო და სასარგებლო პასუხი. შემდეგ მოქმედებას (ძიება თუ პირდაპირი პასუხი, რომელი საძიებო ფრაზა) LLM ამ მიზნიდან გამომდინარე წყვეტს.
- **შიდა მდგომარეობა.** რადგან გარემო *თანმიმდევრულია*, საუბრის ისტორია მარტივ მეხსიერებად გვჭირდება, რომ დამატებითი შეკითხვები მუშაობდეს. ეს სრული სამყაროს მოდელი არ არის (კომპიუტერის რეალურ მდგომარეობას აგენტი ვერ ხედავს და ვერ აფასებს), ამიტომ წმინდა model-based აგენტადაც არ მიგვაჩნია.
- **არ არის utility-based.** არ არსებობს რიცხვითი სასარგებლობის ფუნქცია, რომელიც ალტერნატიულ შედეგებს შეადარებდა.
- **არ არის learning.** აგენტი გამოცდილებით არ სწავლობს და არ უმჯობესდება. მოდელის წონები და ცოდნის ბაზა ფიქსირებულია, ხოლო `reset` მხოლოდ საუბრის ისტორიას ასუფთავებს.

## E. არქიტექტურა

```
 მომხმარებელი (ტერმინალი)
      |  1. პრობლემის ტექსტი
      v
  main.py  ---- ბრძანებები: quit / exit / reset ----+
      |                                              |
      v                                              |
  agent.py : HelpdeskAgent.run_turn()                |
      | 2. messages + ინსტრუმენტის აღწერა            |
      v                                              |
  Ollama /api/chat  (qwen2.5:7b)  <---- 5. ინსტრუმენტის შედეგი ემატება messages-ს
      | 3. LLM წყვეტს: უპასუხოს პირდაპირ თუ გამოიძახოს tool_call
      v
  tools.py : არგუმენტების შემოწმება -> search_knowledge_base()
      | 4. კითხულობს knowledge_base.json-ს, ანიჭებს ქულებს ჩანაწერებს
      v
  უკან LLM-თან -> 6. საბოლოო პასუხი ჩანს ტერმინალში
```

- **LLM** (`qwen2.5:7b`): ერთადერთი გადაწყვეტილების მიმღები. ის წყვეტს, გამოიძახოს თუ არა ინსტრუმენტი, თვითონ წერს საძიებო ფრაზას (query) და საბოლოო პასუხს.
- **აგენტის ციკლი** (`agent.py`): აგზავნის შეტყობინებებსა და ინსტრუმენტის სქემას Ollama-ს `/api/chat`-ზე, კითხულობს ნატიურ `tool_calls` ველს, ასრულებს გამოძახებებს და შედეგებს უკან აბრუნებს `role: "tool"` შეტყობინებებად. ერთ მოთხოვნაზე ინსტრუმენტის გამოძახებებს ზღუდავს `MAX_TOOL_CALLS = 3`-ით, ხოლო თუ მოთხოვნა ჩავარდა, ისტორიას უკან აბრუნებს (rollback).
- **სარეზერვო პარსერი (fallback parser):** თუ მოდელმა ინსტრუმენტის გამოძახება ნატიური ველის ნაცვლად JSON ტექსტად დაბეჭდა, `extract_tool_calls` მაინც ამოიკითხავს მას. გადაწყვეტილებას მაინც LLM იღებს, Python მხოლოდ კითხულობს.
- **ინსტრუმენტი** (`tools.py`): ამოწმებს არგუმენტებს (ტიპი, ცარიელი ხომ არ არის, სიგრძე, დიაპაზონი) და ასრულებს ძიებას. შეცდომები LLM-ს უბრუნდება როგორც `{"status": "error"}`, რომ მან მათზე გულწრფელად მოახსენოს მომხმარებელს.
- **ცოდნის ბაზა** (`knowledge_base.json`): 12 ჩანაწერი (ID, სათაური, keywords, მიზეზები, ნაბიჯები, გაფრთხილებები).
- **უსაფრთხოება:** system prompt კრძალავს იმის თქმას, რომ აგენტმა კომპიუტერი შეამოწმა ან მიზეზი დაადასტურა. კოდში არ არის არცერთი ფუნქცია, რომელიც ოპერაციული სისტემის ბრძანებებს გაუშვებდა.

## F. ინსტრუმენტის დოკუმენტაცია

**ავტორი:** რატი კორძაძე 

**სახელი:** `search_knowledge_base`

**დანიშნულება:** ეძებს ლოკალურ IT ტროუბლშუთინგის ცოდნის ბაზაში და აბრუნებს ყველაზე შესაბამის ჩანაწერებს. როდის გამოიძახოს, ამას LLM წყვეტს.

**პარამეტრები:**

| სახელი | ტიპი | სავალდებულო | აღწერა |
|---|---|---|---|
| `query` | string | დიახ | მოკლე ინგლისური საძიებო ფრაზა ძირითადი სიმპტომებით (მაქსიმუმ 300 სიმბოლო) |
| `max_results` | integer | არა | დასაბრუნებელი ჩანაწერების რაოდენობა, 1-5 (ნაგულისხმევი 3) |

**როგორ მუშაობს ძიება:** საძიებო ფრაზა გადადის პატარა ასოებზე და იყოფა სიტყვებად, შემდეგ იშლება stopword-ები (უმნიშვნელო სიტყვები) და სიტყვები უხეშად მცირდება ფუძემდე (stemming, მაგ. `crashes` -> `crash`). ყოველ ჩანაწერს ქულა ენიჭება: თითოეული keyword-ის ყოველი სიტყვისთვის, რომელიც საძიებო ფრაზაში მოიძებნა, +2 (ამიტომ `high ram usage` უფრო მაღალ ქულას იღებს, ვიდრე მხოლოდ `ram`), ხოლო საძიებო ფრაზის თითოეული სიტყვისთვის, რომელიც სათაურშია, +1. მინიმალურ ქულაზე (2.0) დაბალი ჩანაწერები იშლება, დანარჩენი ქულის მიხედვით ლაგდება და უბრუნდება პირველი `max_results`. მთელი ბაზა არასოდეს ბრუნდება.

**დაბრუნებული მნიშვნელობა (წარმატების შემთხვევაში):**
```json
{"status": "ok", "query": "high ram usage slow",
 "results": [{"id": "KB-001", "title": "High RAM (memory) usage", "score": 13.0,
              "causes": "...", "steps": ["..."], "warnings": ["..."]}]}
```
**შესაბამისი ჩანაწერი არ მოიძებნა:**
```json
{"status": "no_results", "query": "...", "message": "No sufficiently relevant entry was found in the knowledge base."}
```
**შეცდომები:** ფუნქცია პროგრამას არასოდეს აჩერებს. არასწორი არგუმენტები (`query` არ არის მითითებული, ცარიელია ან string არ არის; არასწორი `max_results`; არასწორი JSON string; უცნობი ინსტრუმენტის სახელი) და დაკარგული ან დაზიანებული `knowledge_base.json` აბრუნებს `{"status": "error", "message": "..."}`-ს, რომელსაც LLM ხედავს და მომხმარებელს აცნობებს.

**გამოყენების მაგალითი (რას აგზავნის LLM):**
```json
{"name": "search_knowledge_base", "arguments": {"query": "printer offline not printing"}}
```

## G. ინსტალაცია და გაშვება Windows-ზე

საჭიროა Python 3.12, Git და დაინსტალირებული Ollama. ბრძანებები გაუშვი PowerShell-ში.

```powershell
# 1. ჩამოტვირთე პროექტი და გადადი მის საქაღალდეში
git clone https://github.com/rkordzadze23/helpdesk-triage-agent.git
cd helpdesk-triage-agent

# 2. შეამოწმე Python-ის ვერსია (უნდა იყოს 3.12.x)
python --version

# 3. შექმენი და ჩართე ვირტუალური გარემო
python -m venv venv
.\venv\Scripts\Activate.ps1

# 4. დააინსტალირე დამოკიდებულებები
pip install -r requirements.txt

# 5. შეამოწმე, რომ Ollama მუშაობს (უნდა დაბეჭდოს ვერსიის JSON)
Invoke-RestMethod http://localhost:11434/api/version

# 6. შეამოწმე, რომ მოდელი დაინსტალირებულია (სიაში უნდა იყოს qwen2.5:7b)
ollama list

# 7. თუ მოდელი სიაში არ არის, ჩამოტვირთე
ollama pull qwen2.5:7b

# 8. გაუშვი აპლიკაცია
python main.py
```

Token ან API გასაღები არ არის საჭირო, რადგან მოდელი ლოკალურად მუშაობს.

თუ მე-5 ნაბიჯი ვერ შესრულდა, გაუშვი Ollama აპლიკაცია Start მენიუდან (ან ცალკე ფანჯარაში გაუშვი `ollama serve`).

**თუ PowerShell ბლოკავს `Activate.ps1`-ს** (შეცდომა: "running scripts is disabled on this system"):

- *მუდმივი გადაწყვეტა მხოლოდ შენი მომხმარებლისთვის* (რეკომენდებულია):
  ```powershell
  Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
  ```
- *დროებითი გადაწყვეტა* (მოქმედებს მხოლოდ მიმდინარე PowerShell ფანჯარაზე):
  ```powershell
  Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
  .\venv\Scripts\Activate.ps1
  ```
- *აქტივაციის გარეშე:* გამოიყენე venv-ის Python პირდაპირ:
  ```powershell
  .\venv\Scripts\python.exe -m pip install -r requirements.txt
  .\venv\Scripts\python.exe main.py
  ```

**ოფლაინ ტესტების გაშვება (არასავალდებულო):** `python -m unittest -v`

**ინსტრუმენტის ნედლი შედეგის ჩვენება:** `python main.py --debug`

**როგორ დავრწმუნდეთ, რომ LLM ნამდვილად იძახებს ინსტრუმენტს:** ყოველი გამოძახება ტერმინალში იბეჭდება როგორც `[tool call] search_knowledge_base({...})`, მის შემდეგ კი `[tool result] ...`, საბოლოო პასუხამდე. საძიებო ფრაზას მოდელი წერს, ამიტომ ის გაშვებიდან გაშვებამდე იცვლება. თუ აგენტს მივესალმებით ("hello"), `[tool call]` ხაზი არ უნდა გამოჩნდეს, რაც აჩვენებს, რომ მოდელი თვითონ წყვეტს, სჭირდება თუ არა ძიება.

## H. ინტერაქციის მაგალითი

> **მხოლოდ საილუსტრაციო მაგალითია.** ეს არ არის ჩაწერილი რეალური გაშვების ზუსტი ტექსტი. LLM არადეტერმინისტულია, ამიტომ რეალური პასუხის ფორმულირება განსხვავდება. სტრუქტურა კი (ინსტრუმენტის გამოძახება, შემდეგ ბაზაზე დაყრდნობილი პასუხი) იგივე უნდა იყოს. პროგრამა ინგლისურ ენაზეა ორიენტირებული, ამიტომ მაგალითიც ინგლისურადაა.

```
You: My computer is very slow, and Task Manager shows 95% RAM usage.
Thinking...

  [tool call] search_knowledge_base({"query": "high ram usage slow computer"})
  [tool result] 1 entry: KB-001 (High RAM (memory) usage)

Agent:
**Possible causes** (not confirmed - I cannot inspect your PC)
- Too many open programs or browser tabs, a program using more and more memory (memory leak),
  many startup programs, malware, or not enough installed RAM. (KB-001)

**What to check first**
- Open Task Manager (Ctrl+Shift+Esc) > Processes and sort by the Memory column to see which programs use the most.

**Recommended steps**
1. Save your work and close programs or tabs you do not need.
2. Restart a program whose memory keeps growing, and check for an update.
3. Restart the computer; disable unneeded programs under Task Manager > Startup apps.
4. Run a Windows Security scan.
Warning: do not end processes you do not recognise - this can make Windows unstable.

**Contact IT support if** RAM stays above ~85-90% even with few programs open (the PC may need more RAM)
or the problem returns after these steps.

You: How do I bake a chocolate cake?
  [tool call] search_knowledge_base({"query": "bake chocolate cake"})
  [tool result] no_results: No sufficiently relevant entry was found in the knowledge base.

Agent: The knowledge base has no relevant entry for this. I only help with computer and IT problems...
```

ეს განყოფილება მხოლოდ გეგმაა და **ჯერ არ არის რეალიზებული**. მეორე ეტაპისთვის საჭიროა მინიმუმ 3 ინსტრუმენტი, ამიტომ თემა ისე შეირჩა, რომ მისი გაფართოება შესაძლებელია: ცოდნის ბაზაში ძიების გვერდით შეიძლება დაემატოს ახალი, ერთმანეთისგან განსხვავებული ინსტრუმენტები (მაგალითად, IT მხარდაჭერისთვის გასაგზავნი მოთხოვნის ტექსტის მომზადება ან დისკის ადგილის გამოთვლა მომხმარებლის მიერ მითითებული რიცხვებით). ზუსტი არჩევანი მეორე ეტაპზე დაზუსტდება.
